# Feedback & Issue Reports Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Logged-in users send feedback, bug reports and ideas, with an optional screenshot and automatic context, from a floating help button or from error screens. Admins triage them in an inbox and can turn one into a prefilled GitHub issue.

**Architecture:**
- Pure, shared logic (types, limits, context schema, GitHub URL/draft builder, help-button visibility) lives in `shared/feedback.ts` so the server, the client and the tests all use it.
- The server adds a `feedback` table, a student `POST /api/feedback` (multipart) and admin routes in a new `server/routes/feedback.ts`, plus screenshot storage under `UPLOAD_DIR/feedback/` with a global cap and a daily retention sweep.
- The client adds a small module-level store (`openFeedback(seed?)`) so any code can open the sheet: the help button, error toasts, and a router crash screen.
- The admin inbox is a new admin tab.

**Tech Stack:** Hono on Bun, Drizzle + SQLite migrations, zod, React 19, TanStack Query, shadcn/ui (drawer, dialog, select, toggle-group), react-i18next, bun test.

**Spec:** `docs/superpowers/specs/2026-11-20-feedback-design.md`

## Global Constraints

- Logged-in users only. Admin routes are admin only (403 otherwise).
- Report types are `feedback | bug | idea`. Statuses are `new | in_progress | done`.
- Message 10–4000 characters (code points, trimmed). The screenshot is ≤ 5 MB, `image/webp|jpeg|png`, checked by magic bytes. The context JSON is ≤ 8 KB, strict, with unknown keys stripped. Context string caps: path 300, titles 200, error message 500, stack 4096, user agent 400.
- `githubUrl` must start with `https://github.com/` (≤ 300 characters) or be null.
- Rate limit for `POST /api/feedback`: **5 per hour and 20 per day per user**.
- Screenshots are stored at `UPLOAD_DIR/feedback/<id>.<ext>` and served only to admins with `Cache-Control: private, no-store`. Deleting a report deletes its file.
- **Retention:** the screenshot of a report that has been `done` for ≥ 90 days (by `updatedAt`) is deleted and the column set to null. The sweep runs on start and every 24 h. **Global cap of 500 MB** on `UPLOAD_DIR/feedback`. Above it, the report is saved without the screenshot and the response is `{ id, screenshotDropped: true }`.
- The GitHub draft never contains the reporter's name or email. Email-like strings in the message and context become `[email]`. The URL is `https://github.com/<repo>/issues/new?title=&body=&labels=`, kept under 8000 characters by truncating the body and appending `\n\n_(ingekort)_`. The repo comes from env `GITHUB_REPO`, default `SilkePilon/windesheim-readers`.
- **Help button visibility:** shown only inside `AppLayout`, logged in, and never on `/lesson/:id` with any `?view=`. `StudyShell` routes (cards, quiz, review, battle room) never render `AppLayout`, so it is absent there automatically.
- App version: `__APP_VERSION__` = env `APP_VERSION`, else `git rev-parse --short HEAD`, else `"dev"`.
- All copy is in `src/locales/nl.ts` and `en.ts`. Mobile-first, light and dark themes, Speelveld styling.
- No new runtime dependencies.

## Review Focus

- A screenshot named `.png` whose bytes are actually HTML/SVG gets 400 `BAD_IMAGE`, and nothing is written to disk. (Task 2 test.)
- The 6th report within an hour gets 429 `RATE_LIMITED`, and no row or file is created. (Task 2 test.)
- An admin deletes a report whose screenshot file is already gone: 200, with no crash. (Task 2 test.)
- An error toast for a 400 validation error offers **no** "Melden" action, while a 500 and a network `TypeError` do. (Task 5 test on `isReportable`.)
- A long message plus a stack trace keeps the GitHub URL under 8000 characters, and the draft contains neither the reporter's email nor the name. (Task 1 test.)

export const FEEDBACK_TYPES = ["feedback","bug","idea"] as const; export type FeedbackType = …;
export const FEEDBACK_STATUSES = ["new","in_progress","done"] as const; export type FeedbackStatus = …;
export interface FeedbackContext { path: string; readerTitle?: string; lessonCode?: string; lessonTitle?: string;
  appVersion: string; userAgent: string; browser: string; viewport: string; locale: string; theme: string;
  standalone: boolean; error?: { message: string; status?: number; code?: string; apiPath?: string; stack?: string } }

### Task 2: Server: table, routes, storage, retention

**Files:**
- Modify: `server/db/schema.ts` (table `feedback`)
- Create: `server/db/migrations/0007_feedback.sql` via `bun run db:generate` (and its snapshot and journal entry)
- Modify: `server/lib/input.ts`, `server/limits.ts`, `server/env.ts`, `server/app.ts`
- Create: `server/routes/feedback.ts`, `server/lib/feedback-store.ts`
- Test: `tests/feedback-app.test.ts` (follow the login and server bootstrap pattern of `tests/input-limits-app.test.ts`), `tests/feedback-store.test.ts`

**Interfaces:**
- Consumes: Task 1's types, `LIMITS.feedback`, `defaultIssueDraft` (not used on the server).
- Produces:
  - **Table:** `feedback(id text pk, user_id text null FK user ON DELETE SET NULL, type text, message text, context text json, screenshot text null, status text default 'new', github_url text null, created_at, updated_at)` with an index on `(status, created_at)`.
  - **Env:** `env.githubRepo`.
  - **Rate limit:** `limits.feedback = rateLimit({ name: "feedback", rules: [{limit:5, windowMs:HOUR},{limit:20, windowMs:DAY}] })`. Use `24*HOUR` if there's no DAY constant.
  - **Body cap:** `POST /api/feedback` uses a new cap `LIMITS.body.feedback = 6 * 1024 * 1024`, added to the `bodyCaps` branch in `app.ts`.
  - **Routes:**
    - `POST /api/feedback` → 201 `{ id, screenshotDropped?: true }`;
    - `GET /api/admin/feedback?status=&type=` → `{ repo: string, items: FeedbackRow[] }`, where `FeedbackRow = { id,type,message,context,status,githubUrl,hasScreenshot,createdAt,updatedAt, reporter: { name, email } | null }`, newest first;
    - `GET /api/admin/feedback/count` → `{ new: number }`;
    - `PATCH /api/admin/feedback/:id` with `{ status?, githubUrl? }` (at least one) → `{ ok: true }`, or 404;
    - `DELETE /api/admin/feedback/:id` → `{ ok: true }`, or 404;
    - `GET /api/admin/feedback/:id/screenshot` → the image bytes with the correct content type, or 404.
  - **Store** (`feedback-store.ts`):
    - `sniffImage(bytes: Uint8Array): "webp"|"jpeg"|"png"|null`;
    - `feedbackDirBytes(): Promise<number>`;
    - `saveScreenshot(id, bytes, ext): Promise<string>`;
    - `deleteScreenshot(name): Promise<void>` (ignores a missing file);
    - `sweepFeedbackScreenshots(now = Date.now()): Promise<number>` (returns the count deleted);
    - `FEEDBACK_DIR_CAP = 500 * 1024 * 1024`;
    - `RETENTION_MS = 90 * 24 * HOUR`.
  - **Zod in `input.ts`:**
    - `feedbackContext` (strict object, strip unknown, the caps from Global Constraints);
    - `feedbackCreate = { type, message (trim, code-point length), context }`;
    - `feedbackPatch`.

- [ ] **Step 1: Write the failing tests.**
  - **Store tests:**
    - `sniffImage` recognises the PNG, JPEG and WebP signatures and returns null for `<svg` and `<html` bytes;
    - the sweep deletes only the screenshots of `done` rows whose `updatedAt` is ≥ 90 days old, nulls the column, and leaves `new` rows untouched.
  - **App tests:**
    - create without a screenshot → 201 and a row with status `new`;
    - create with a 1×1 PNG → a file exists, and the admin GET of the screenshot returns `image/png` with `no-store`;
    - a fake PNG (HTML bytes) → 400 `BAD_IMAGE` and no file;

    - context with an unknown key → 201, and the stored context lacks that key;
    - context > 8 KB → 400 `VALIDATION`;
    - 6th POST in an hour → 429 `RATE_LIMITED`;
    - a student on any `/api/admin/feedback*` route → 403;
    - list filters by status, count returns the new count, PATCH status and githubUrl work, a githubUrl of `http://evil` → 400;
    - DELETE removes the row and the file, and DELETE when the file is already gone → 200;
    - when `feedbackDirBytes` exceeds the cap (spy or stub), create → 201 `{ screenshotDropped: true }` and no file is written.
